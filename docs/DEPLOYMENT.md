# ClimatePilot 上线与运维手册

> 本文档面向**要在一套真实采暖系统上启用 ClimatePilot 的人**。
> 它不重复 README 的功能介绍，只讲：怎么安全上线、怎么判断它工作正常、出问题怎么办。
>
> 阅读顺序建议：第 1 节（风险）→ 第 2 节（核验）→ 第 3 节（观察期）→ 第 4 节（切换协调）。

---

## 1. 先读这一段：这套系统可能造成什么后果

ClimatePilot 会**写你的锅炉**。写错水温与写错启停一样危险。在开始之前，请确认你接受以下事实：

| 风险 | 说明 | 缓解 |
|---|---|---|
| **HA 是唯一热源请求方** | 若锅炉采暖请求只由 HA 发出，**HA 停机/断电/网络中断会导致采暖停止** | 确认锅炉有本地备用控制链路，或明确接受该风险 |
| **生活热水被误关** | 若 `set_hvac_mode: off` 同时关闭了生活热水或防冻 | 第 2 节核验项 ①，未确认则集成不写锅炉 |
| **供水温度被误设** | 若 `set_temperature` 实际改的是室温或生活热水 | 第 2 节核验项 ② |
| **最小循环流量不足** | 全部阀门关闭时锅炉可能高温保护或频繁启停 | 第 2 节核验项 ③，属**水力硬件问题**，软件无法替代 |
| **地面过热** | 供水温度超过地暖设计上限可能损伤地面材料 | 曲线 `supply_max` 必须服从地暖设计限制 |

**软件延迟、辅助负载或温度判据不能替代**：锅炉最小流量保护、可靠旁通/水力解耦、过热保护、水泵后循环。这些是硬件安全功能。

## 2. 上线前必须完成的核验

### 2.1 从 HA 开发者工具采集真实接口信息

先在 **开发者工具 → 状态**里逐个确认，**不要假设**：

```yaml
# 需要记录的属性
climate.rinnai_heating_control:
  hvac_modes:        # 例如 [heat, auto, dry, off]
  min_temp / max_temp:
  target_temp_step:
  current_temperature:   # 林内可能为 null

climate.<每个房间>:
  hvac_modes:
  min_temp / max_temp / target_temp_step:
  hvac_action:           # 是否可靠？是否随实际要热变化？
  current_temperature:
```

**已知的现场事实**（本仓库的参考安装）：

| 实体 | 关键属性 |
|---|---|
| `climate.rinnai_heating_control` | `hvac_modes: [heat, auto, dry, off]`，`min_temp: 40`，`max_temp: 82`，`target_temp_step: 1`，`current_temperature: null`，`supported_features: 1`（**只支持目标温度，无 hvac_action**） |
| KNX 房间温控器 | `hvac_modes: [heat, off]`，`min_temp: 16.0`，`max_temp: 26.0`，`target_temp_step: 0.5`，`supported_features: 385` |

注意锅炉 `supported_features: 1`：它**不上报 `hvac_action`**。因此：
- 锅炉自身不能作为"是否在加热"的判断依据；
- 采暖需求必须来自**房间温控器**的 `hvac_action`，或专用的请求对象；
- 燃烧统计应使用独立的燃烧状态传感器（林内集成提供 `sensor.heating_burning_state` / `sensor.hot_water_burning_state`，取值 `Standby` / `Heating Water` / `Burning` / `Error`）。

### 2.2 三项设备语义核验（配置流程第 3 步）

- [ ] **① 关闭采暖模式不会影响生活热水与防冻保护**
      实测方法：在锅炉上单独把采暖切到 off，观察生活热水与防冻是否仍然正常。
- [ ] **② `set_temperature` 对应采暖供水温度**
      实测方法：改一次水温设定，观察 `sensor.heating_temperature`（或锅炉面板）是否随之变化，而**不是**室温或热水温度。
- [ ] **③ 最小循环流量与旁通/水力解耦已由安装方验收**
      需安装方书面确认：最小流量、循环泵扬程、全阀关闭工况、差压旁通或水力耦合罐、膨胀水箱、地暖最高允许供水温度、锅炉后循环。

> **三项全部为「是」之前，ClimatePilot 处于仅建议模式**：它会计算并显示建议水温，但**不会**写锅炉。这是设计上的硬门，不是可以绕过的提示。
>
> 若第 ① 或 ② 项**无法确认**，正确做法是**永久保持仅建议模式**：让 ClimatePilot 只管房间温度与诊断，锅炉启停交回原有逻辑。

### 2.3 冲突检查

- [ ] 原「地暖全能主控」蓝图（`automation.di_nuan_quan_neng_zhu_kong`）**已停用**
      否则蓝图与集成会同时写同一批实体。检查方式：把该自动化 `turn_off`，或直接删除。
- [ ] `input_boolean.floorheating_enabled`（总地暖允许）等旧辅助实体的归属已明确（由谁读写）。
- [ ] 没有其它自动化在写同一批 `climate` 实体：
      ```bash
      # 用 ha_search 查引用
      ha_search("climate.livingroom_floorheating")
      ```

## 3. 观察期（建议 ≥ 3 天，覆盖一次完整降温过程）

以 `observe` 模式运行。此模式下集成**只读**，不写任何实体。

### 3.1 每天检查什么

| 检查项 | 在哪看 | 期望 |
|---|---|---|
| 决策是否合理 | `climate.<system>_thermostat` 属性 → `zone_reason_codes` / `zone_sources` | 每间房的来源符合预期（日程 / 手动 / 固定模式） |
| 有效目标是否正确 | `sensor.<room>_effective_setpoint` | 等于你期望的温度，且落在允许范围内 |
| 与 KNX 实际值是否一致 | 对比 `actual_setpoint`（实体属性）与面板显示 | 一致；不一致说明有回读延迟或写入回声未识别 |
| 需求判定是否准确 | `sensor.<system>_active_zones`、`binary_sensor.<room>_heat_request` | 房间实际要热时该房间为 on；**`heat` 模式本身不算需求** |
| 手动操作是否被正确识别 | 手动改一次 KNX 面板温度 → 看 `binary_sensor.<room>_manual_override` | 应在数秒内变 on，且 `sensor.<room>_setpoint_source` = `manual` |
| 天气补偿是否合理 | `sensor.<system>_suggested_supply_temp` | 室外冷 → 水温高；数值在 `supply_min`/`supply_max` 之间 |
| 数据质量 | `binary_sensor.<system>_degraded` | 应为 off；on 表示有实体失联或状态不确定 |

### 3.2 三个必须通过的验收动作

设计文档 V0.1 的交付标准，请在观察期内逐条实测：

1. **手动温度不被巡检改回**
   在面板上把某房间设为 21.5℃，等 **≥ 30 分钟**（超过最小写入间隔），确认 `sensor.<room>_effective_setpoint` 仍是 21.5℃，且 `setpoint_source` 仍是 `manual`。
2. **重启后覆盖期限保持**
   设一个「固定 2 小时」覆盖，等 45 分钟后重启 HA，确认剩余期限约为 1 小时 15 分（而不是重新开始 2 小时）。
3. **失联不误关炉**
   在 `observe` 模式观察到 `binary_sensor.<system>_degraded` 变 on 时，确认没有任何针对锅炉的写入产生。

### 3.3 若观察期发现问题

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 房间一直显示「手动覆盖」 | 回读值与我们写入的值不匹配，被判定为外部修改 | 检查该温控器的 `target_temp_step` 与容差；必要时调大该房间的 `tolerance` |
| 我们的写入被当成用户操作 | 同上，或设备回读延迟超过确认窗口 | 调大确认窗口（`DEFAULT_PENDING_TIMEOUT`）或该房间容差 |
| 需求数长期为 0 | 温控器不上报 `hvac_action` | 为该房间配置请求对象（`hvac_action_entity`，适配模式） |
| 需求数长期偏高 | `hvac_action` 不可靠 | 同上；或临时仅用观察模式判断 |
| 建议水温不变化 | 室外传感器过期 | 检查 `sensor.<system>_outdoor_temperature` 的可用性与 `last_updated` |

## 4. 切换到协调模式

前提：第 2 节三项核验全部为「是」，且第 3.2 节三个验收动作全部通过。

1. 在 `select.<system>_control_mode` 选择 **协调**
2. 集成会自动重新评估；`climate.<system>_thermostat` 属性中的 `heat_source_semantics_verified` 应为 `true`
3. **首个 24 小时密切观察**：

| 观察项 | 期望 |
|---|---|
| `sensor.<system>_heating_state` | 在 `idle → prepare → heating → satisfied → idle` 之间正常流转 |
| 锅炉实际点火 | 与 `sensor.<system>_active_zones` > 0 相关 |
| 生活热水 | **完全不受影响**（这是核验项 ① 的现场复核） |
| `sensor.<system>_burner_starts_24h` | 不应异常高（短循环征兆） |
| `binary_sensor.<system>_short_cycle_alert` | 应为 off |

### 状态机说明

```
OBSERVE   只观察，不写任何实体
IDLE      无需求
PREPARE   有需求，等待阀门预开（无位置反馈，此等待只是运行协调，不能证明阀门已开）
HEATING   已发出采暖请求
SATISFIED 需求结束，撤销请求中（含水泵后循环）
DEGRADED  通讯异常 / 状态不明 → 停止新写入，人工接管
```

**重要**：全部执行器关闭时，集成会**立即**撤销采暖请求，**不会**用"最短运行时长"强迫燃烧器继续加热。最短运行时长只用于抑制抖动，不用于延长燃烧。

## 5. 日常运维

### 5.1 常用操作

| 需求 | 操作 |
|---|---|
| 某房间临时改温 | 直接在 KNX 面板或 HA 改；集成会识别为手动覆盖并保护 |
| 立即回到自动 | `button.<room>_resume_auto`，或调用 `climatepilot.resume_auto` |
| 全部房间回到自动 | 调用 `climatepilot.resume_auto`（不带 `zone_id`） |
| 临时暂停全部控制 | `select.<system>_control_mode` → **暂停**（保留状态与覆盖） |
| 立刻重算 | `button.<system>_reassess`，或 `climatepilot.reassess` |
| 手动指定水温 | `number.<system>_supply_temperature_override`（需已核验语义） |

### 5.2 手动覆盖的三种恢复策略

每个房间独立配置：

| 策略 | 行为 | 适用 |
|---|---|---|
| **下个日程节点**（默认） | 在下一个真实日程切换点恢复；日程空缺时按「直到手动取消」 | 大多数房间 |
| **固定时长** | 例如 2 小时，存绝对到期时刻，重启不延长 | 客房、临时加温 |
| **一直保持** | 直到用户点「恢复自动」 | 需要长期固定的房间 |

### 5.3 辅助热负载（客厅陪跑）

替代了蓝图里「当前室温 +2℃」的无限追涨。启用前理解它的边界：

- 以**房间日程目标**为基准加一个小偏移（默认 +0.5℃），**与实测室温无关**；
- 有绝对上限、退出回差、最短切换间隔、夜间禁止；
- 其他房间需求结束时**明确归位**；
- 手动覆盖期间**不生效**；
- **它不是锅炉最小流量的安全保证** —— 客厅阀门关闭时仍必须有水力保障。

### 5.4 让室外温度进入长期统计（V0.5 用气分析的前提）

**背景。** `recorder.purge_keep_days`（本机 30 天）到期后会清除明细数据。只有带
`state_class` 的实体才会另存一份**永久**的长期统计。和风天气集成创建的
`sensor.heweather_outside_temperature` **没有** `state_class`，因此：

- `sensor.gas_meter` 永久保留（它本来就是 `total_increasing`）；
- 但**解释它的室外温度会在 30 天后被清除**。

结果是过一段时间后，你会只剩一堆无法解释的燃气数字 —— 而
`sensor.cp_gas_per_degree_day` 正是靠室外温度算出来的。

**做法。** 在 **`packages/heweather_sensors.yaml`** 的 `homeassistant: customize:` 段
（该文件本来就负责这两个天气传感器的定制）追加：

```yaml
    sensor.heweather_outside_temperature:
      state_class: measurement
      device_class: temperature
```

**为什么是 `customize:` 而不是改集成：** 该实体属于 HACS 的 `heweather` 集成，
改它的源码会在下次更新时被覆盖。

**为什么 `customize:` 能生效：** customize 的值会合并进 **state attributes**
（`helpers/entity.py` 的 `attr |= custom`），而统计模块正是从 state attributes 读取
`state_class`（`components/sensor/recorder.py` 的 `state.attributes.get(...)`）。
两条路径吻合。另外 `_CUSTOMIZE_DICT_SCHEMA` 带 `extra=vol.ALLOW_EXTRA`，
所以 `state_class` 这种"非标准"键不会被校验拒绝。

**为什么放在 package 里而不是 `configuration.yaml`：**
`core_config.py` 会把每个 package 的 `homeassistant: customize:` 合并进全局
（`cust_exact.update(...)`），所以两者等价，但 package 文件小、易读、易回滚。

**验证（务必做，不要只看属性）。** 属性存在 ≠ 统计在写。用 HA 的 WebSocket 命令
`recorder/list_statistic_ids` 确认出现了该 `statistic_id`，且 `source` 为 `recorder`：

```
statistic_id: sensor.heweather_outside_temperature
source:       recorder        <- 长期统计（永久）
has_mean:     true
unit_class:   temperature
```

再用 `recorder/statistics_during_period` 看是否真有数值：

```
13:00  mean=26.63  min=26.0  max=28.0
```

≥1 个小时点即表示统计已在累积。

**注意事项：**

- `measurement` 是 `device_class: temperature` **唯一**允许的 `state_class`
  （见 `DEVICE_CLASS_STATE_CLASSES`）。写别的值会产生 "impossible considering
  device class" 告警。
- **单位字符串不能变。** 若该集成某天把 `°C` 改成别的单位，HA 会抑制统计并告警 ——
  这是它唯一会抱怨的方式。
- 这两项都是**用户侧配置**，集成本身**不会**修改任何 `configuration.yaml`。

## 6. 故障处理

### 6.1 诊断导出

**设置 → 设备与服务 → ClimatePilot → ⋯ → 下载诊断**。

导出内容包含：控制模式、每个房间的仲裁结果与原因码、手动覆盖详情、待确认命令状态、热源能力与判定、天气补偿结果、燃烧统计。**经纬度与任何名称含 secret/token/password 的字段会被脱敏。**

报 issue 时请附上该文件 —— 原因码是定位问题的关键。

### 6.2 常见故障

| 症状 | 排查 |
|---|---|
| 集成加载失败 | 设置 → 系统 → 日志，搜 `climatepilot`。检查 HA 版本 ≥ 2025.1 |
| 房间温度不被调整 | ① `select.<system>_control_mode` 是否为**协调**；② `binary_sensor.<room>_manual_override` 是否 on；③ 该房间 `feedback_quality` 是否 `unavailable`；④ 启动宽限期（默认 120s）是否已过 |
| 房间显示手动覆盖但没人动过 | 见 3.3 第 1、2 行 |
| 锅炉不启动 | ① 三项语义核验是否全为「是」；② `sensor.<system>_active_zones` 是否 > 0；③ 是否处于需求消抖/阀门预开等待期；④ `binary_sensor.<system>_degraded` 是否 on |
| 锅炉频繁启停 | 看 `sensor.<system>_burner_starts_24h` 与短循环告警；考虑加大需求消抖与最短停机时间；**同时检查水力条件** |
| 水温不变化 | ① `sensor.<system>_suggested_supply_temp` 是否变化；② 是否处于建议模式；③ 是否未过最小下发间隔（默认 30 分钟）；④ 变化是否小于回差（默认 1℃） |
| 生活热水受影响 | **立即切到「暂停」**，并复核核验项 ①。这是最高优先级问题 |

### 6.3 紧急停止

| 手段 | 效果 |
|---|---|
| `select.<system>_control_mode` → **暂停** | 停止全部写入，保留状态与手动覆盖 |
| 卸载集成 | 停止全部写入；**不会**自动撤销已发出的采暖请求（见下） |
| 关闭 HA | **若 HA 是唯一请求方，采暖会停止** |

**关闭集成时的行为**：集成停止写入，但锅炉会保持它最后收到的模式。若你希望明确撤销采暖请求再卸载，请先在协调模式下等 `sensor.<system>_heating_state` 回到 `idle`，或手动在锅炉上切到 off。

## 7. 调参参考

以下为初始建议值，**均需现场验证**，不是热负荷计算结论。

### 7.1 天气补偿曲线

温州湿式地暖的起点（**待验证**）：

| 室外温度 | 供水温度 |
|---|---|
| 0℃ | 45℃ |
| 15℃ | 40℃ |

- `supply_min` / `supply_max`：服从锅炉自身参数与地暖设计限制（A2747FF 的可设范围需与说明书交叉核验）；
- 回差初始 1℃，最小下发间隔初始 30 分钟；
- 夜间水温回落默认 0℃（即不回落）。

**房间达温效果优先于曲线理论值**：如果房间到不了目标温度，先提 `supply_design`，而不是改室温目标。

### 7.2 时间参数

| 参数 | 默认 | 含义 |
|---|---|---|
| 需求开启消抖 | 60 s | 需求出现后等待多久才动作 |
| 需求关闭消抖 | 300 s | 防抖动，不是最小运行时长 |
| 阀门预开等待 | 180 s | 无位置反馈时的运行协调 |
| 最短开机 | 300 s | 抑制抖动 |
| 最短停机 | 300 s | 抑制抖动 |
| 水泵后循环 | 180 s | 需求结束后的后循环窗口 |
| 最小写入间隔 | 60 s | 每房间 |
| 确认窗口 | 90 s | 等待设备回读 |
| 启动宽限期 | 120 s | HA 启动后不立即覆盖 |
| 周期一致性校验 | 900 s | 事件驱动之外的兜底巡检 |

### 7.3 燃烧诊断

- 短循环阈值默认 **300 秒**；
- **默认仅告警**，不会凭统计值修改锅炉内部安全流程；
- 生活热水燃烧**不计入**采暖短循环判定，但会在 `includes_dhw` 中标记 —— 避免把洗澡点火误判为地暖短循环；
- 若你的设备只提供通用燃烧状态，统计会标记为「总燃烧次数，含可能的生活热水」。

### 7.4 V0.2 诊断：怎么看、怎么处理

> **先读这句：V0.2 的全部诊断都是"看"的，不是"做"的。**
> `cycling_quality`、`comfort_verdict`、`comfort_advice`、`dominant_zone_combination`
> 只**展示**判据与建议，**集成不会据此自动修改锅炉**——不会自动改水温、不会自动启停、
> 不会自动改房间目标。技术设计方案第 8 节要求短循环**默认仅告警**，该约束在 V0.2 继续适用。
> 下面的处置建议请**你自己判断后手动执行**。
>
> 另：V0.2 **未部署到实机、未经现场验证**。下面的阈值是设计建议值，
> 需要在你的系统上跑满一个完整降温过程后才谈得上可信。

#### 7.4.1 新增的诊断实体

| 实体 | 取值 | 看什么 |
|---|---|---|
| `sensor.<system>_dominant_zone_combination` | 组合键或 `none` | 24 小时内占比最高的需求组合，如 `living_room+master_bedroom` |
| `sensor.<system>_zone_combination_count` | 整数 | 出现过多少种不同组合。**种类越多说明需求越零碎** |
| `sensor.<system>_combinations_24h` | JSON（属性） | 组合 → 占比明细，定位具体是哪些房间在同时要热 |
| `sensor.<system>_cycling_quality` | `good` / `fair` / `poor` / `unknown` | 采暖燃烧质量分级，见 7.4.2 |
| `sensor.<system>_unexplained_burns_24h` | 整数 | 24 小时内**没有任何分区要热**却点火的次数 |
| `sensor.<room>_comfort_verdict` | `ok` / `overheating` / `underheating` / `unknown` | 该房间的舒适判定 |
| `sensor.<room>_comfort_advice` | 建议码 | 该房间该怎么处理，见 7.4.3 |
| `binary_sensor.<room>_overheating` | on / off | 持续高于目标 |
| `binary_sensor.<room>_underheating` | on / off | 持续低于目标**且确实在要热** |

`comfort_verdict` 为 `unknown` 表示**读数缺失**（`current_temperature` 或目标为
`null`/不可用），不是"正常"。集成**绝不把缺失值当 0℃**——若长期为 `unknown`，
先修传感器，不要据此判断房间冷热。

#### 7.4.2 `cycling_quality` 的 good / fair / poor 阈值

分级只看**采暖燃烧**的平均单次时长（生活热水燃烧**不参与**判定，
所以洗澡点火不会把地暖质量拉低）：

| 等级 | 判据 | 含义 |
|---|---|---|
| `good` | 平均单次燃烧 **≥ 600 秒** | 单次燃烧足够长，锅炉在稳定工况下运行 |
| `fair` | 平均单次燃烧 **≥ 300 秒** 且 < 600 秒 | 偏短，值得观察 |
| `poor` | 平均单次燃烧 **< 300 秒** | 典型短循环征兆：频繁启停、效率下降、部件磨损加快 |
| `unknown` | 窗口内没有采暖燃烧 | 无数据，不是"良好" |

阈值来自 `const.py` 的 `DEFAULT_CYCLING_GOOD_SECONDS = 600.0` 与
`DEFAULT_CYCLING_POOR_SECONDS = 300.0`。实体属性里的 `cycling_quality_reason`
会给出人类可读依据（例如 `average 245s over 6 heating burns`），
**请以它为准**，不要只看等级字母。

看到 `poor` 时的排查顺序：

1. 先看 `sensor.<system>_zone_combination_count` 与 `combinations_24h`：
   需求组合越零碎、切换越频繁，锅炉越容易被反复点火又熄火；
2. 再看 `sensor.<system>_unexplained_burns_24h`：若明显 > 0，
   说明有**不受集成的分区需求驱动**的点火（生活热水、锅炉自身逻辑、
   或未纳入 ClimatePilot 的其它区域），这类点火不归集成管，
   也不应该靠改补偿曲线去"修"；
3. 最后才考虑调 7.2 的时间参数（加大需求消抖、延长最短停机）；
4. **同时检查水力条件**——最小流量不足、旁通缺失同样会造成短循环，
   那是硬件问题，软件参数改不掉。

> 与 V0.1 的关系：`binary_sensor.<system>_short_cycle_alert` 的语义**未变**，
> 仍然只看采暖与未知类型的燃烧、仍然**默认仅告警**。
> `cycling_quality` 是同一批数据的"质量分级"视图，不是新的控制入口。
> `sensor.<system>_unexplained_burns_24h` 与 V0.1 已有的
> `burns_without_demand_24h` 是同一统计的显式命名，两个键都会保留。

#### 7.4.3 `comfort_advice` 每个码该怎么处理

触发条件（`const.py` 冻结的默认值，**当前不可在 UI 调整**）：

| 判定 | 条件 |
|---|---|
| 过热 | 室温高于有效目标 **≥ 1.0℃**，持续 **≥ 30 分钟** |
| 欠温 | 室温低于有效目标 **≥ 1.5℃**，**且该房间确实在要热**，持续 **≥ 60 分钟** |
| 窗口 | 最近 24 小时，每 5 分钟最多记一个样本 |

| 建议码 | 含义 | 你该做什么 |
|---|---|---|
| `raise_supply_temperature` | 房间**在要热、但长期达不到目标**——这是**供热能力不足**的征兆 | 考虑**提高供水温度**（或先提 `supply_design` 曲线点）。这是唯一"改水温可能有用"的码 |
| `check_hydraulics_or_balancing` | 房间**偏冷但没有在要热**——不是水温不够，而是**热没送到该房间** | **不要改水温**。检查该房间的**阀门 / 执行器是否真的打开**、KNX 输出与阀体动作是否一致、**水力平衡**是否把这一路压得太低、该房间的日程或模式是否根本没让它要热 |
| `lower_supply_temperature` | 房间过热，**同时还有别的房间在要热** | 说明当前水温对其他房间偏高。可考虑**下调供水温度**或收窄补偿曲线；注意降温会影响还在要热的房间，改完要回看它们是否转为欠温 |
| `check_schedule_or_override` | 房间过热，**且没有其它房间在要热** | 水温不是原因（没人要热时锅炉本不该工作）。检查**日程/固定模式**是否把目标设低了，或存在**手动覆盖**未恢复——看 `sensor.<room>_setpoint_source` 与 `sensor.<room>_override_remaining` |
| `none` | 判定为 `ok`，或该房间无有效读数（`unknown`） | 无需处理 |

**两个最容易搞反的码**：

- `check_hydraulics_or_balancing` **不是**"水温再高一点就好了"。
  房间没在要热却偏冷，提高水温只会让**其它**房间过热，
  该房间依然冷——问题在阀门、执行器或水力平衡。
- `lower_supply_temperature` 与 `check_schedule_or_override` 的区别在于
  **有没有别的房间在要热**：有人要热 → 可能是水温偏高；
  没人要热 → 一定是日程或手动覆盖的问题，与水温无关。

#### 7.4.4 组合零碎时的读法

`sensor.<system>_zone_combination_count` 持续偏高（例如一天内十几种组合）
说明各房间需求高度不同步。这本身不是故障，但会：

- 让锅炉点火次数上升、单次燃烧变短（`cycling_quality` 转 `fair`/`poor`）；
- 让"主导组合"的占比变低，说明**不存在稳定的主力采暖时段**。

若 `dominant_zone_combination` 为 `none` 且 `active_zones` 长期为 0，
请对照第 3.1 节复查需求判定（`hvac_action` 是否可靠），
而不是去动水温参数。

### 7.5 V0.3 探头诊断：怎么看、怎么处理

> **先读这两句（安全相关）：**
>
> 1. **外贴探头只作监测/优化输入，绝不承担锅炉安全停机功能。**
>    探头损坏、断线、读数异常**不会**改变集成的任何写入决策 ——
>    不改变房间目标、不改变锅炉启停、不改变供水温度。
>    锅炉的最小流量保护、过热保护与防冻逻辑**始终由锅炉自身负责**。
>    **如果你想让探头触发保护动作，请在锅炉/ KNX 侧独立实现，不要依赖本集成。**
> 2. **ΔT 不是热功率。** 供回水温差**不能**用来推算真实热效率或热输出。
>    ΔT 只是流动与冷凝工况的**间接**指标。集成所有输出都带
>    `is_power_measurement = False` 与原因码 `REASON_NOT_A_POWER_MEASUREMENT`。
>
> 另：V0.3 **未部署到实机、未经现场验证**，也尚未在真实 DS18B20 上标定。
> 下面的阈值是设计建议值。

#### 7.5.1 探头安装要求

探头装在哪里，直接决定这些诊断有没有意义：

| 要求 | 说明 |
|---|---|
| **位置** | 锅炉**外部**的**采暖供、回水金属直管**上 |
| **固定** | 导热固定（金属面清洁 + 导热硅脂/金属箔 + 扎带压紧），探头感温面**紧贴**管壁 |
| **保温** | 固定后**必须**在探头外**包保温**，否则读数会被环境温度拉偏，ΔT 直接失真 |
| **不要装在哪** | 生活热水管、锅炉**内部**管段、塑料管、阀门/泵体上（热惯性大、读数滞后） |
| **双探头优于单回水探头** | 只装回水、供水用锅炉自身读数时，两者**采样时刻与位置都不同**，算出的 ΔT 会包含系统误差。**供回水成对安装**才能让 ΔT 可信 |
| **传感器** | DS18B20（防水封装 + 独立总线），走 ESPHome；避免与强电并行走线 |

**为什么强调"金属直管 + 保温"**：ΔT 是两个温度相减的结果，
每一路的固定误差都会**直接进入差值**。夹在保温层外面、贴在阀门上、
或者两路探头热时间常数差很多，都会让 ΔT 在锅炉启停瞬间出现假峰谷。

#### 7.5.2 85℃ 哨兵：最重要的单点检查

**DS18B20 在转换失败或总线断开时，报出的恰好是 85.0℃。**
这是芯片上电复位后的默认寄存器值，不是一个"合理但偏高"的温度。

集成在 `abs(value - 85.0) <= 0.5` 时把它判为 **`implausible`（数值不可信）**，
**不是**"一根很热的管子"。这一条非常关键，因为天真的实现会：

- 报出一个**根本不存在的锅炉故障**（"供水 85℃ 过热"）；
- 或算出一个**巨大的 ΔT**（85 − 40 = 45℃），看起来像"水力很成功"，实则纯属噪声。

`85.0` 与容差 `0.5` 来自 `const.py` 的 `DS18B20_ERROR_C` / `DS18B20_ERROR_TOLERANCE`。

> **看到 `binary_sensor.<system>_probe_fault` 亮起时，先查接线，不要以为锅炉坏了。**
>
> 排查顺序：
> 1. 看 `sensor.<system>_delta_t_quality` 是不是 `implausible` —— 若是，基本可断定是 85℃ 哨兵；
> 2. 查 ESPHome 设备是否在线、DS18B20 总线接线是否松动/进水/过长；
> 3. 查探头供电与上拉电阻；
> 4. **不要**因为一个 85℃ 读数去动锅炉参数或停炉 —— 探头故障不是锅炉故障。

#### 7.5.3 探头质量标签（`delta_t_quality`）

| 取值 | 含义 | 你该做什么 |
|---|---|---|
| `valid` | 读数可信 | 正常使用 |
| `stale` | 读数超过 `probe_stale_seconds`（默认 900 秒）未更新 | 查 ESPHome/网络；诊断暂时不可信，**采暖不受影响** |
| `implausible` | **85℃ 哨兵**、越界、或两路探头偏差过大 | 查接线（见 7.5.2）。偏差过大时**两路都会标为 `implausible`** |
| `frozen` | **仅在锅炉燃烧时**数值长时间完全不变 | 探头可能卡死或脱离管壁；冷却空闲时不会误报 |
| `probe_unavailable` | 实体缺失/不可用/非数值 | 检查实体 id 是否正确、设备是否在线 |

> **为什么是 `probe_unavailable` 而不是 `unavailable`**：`unavailable` 是 Home Assistant 的
> **保留字面量**。任何实体发布它，HA 会把它渲染成**真正的"实体不可用"**（灰掉，
> 与集成坏掉无法区分）。若用它表示"探头没读数"，这个传感器就永远显示为"ClimatePilot 坏了"，
> 恰好抹掉了它存在的意义。所以在 UI 上你会看到 **"无探头读数"** 这个状态 ——
> 它表示**探头没在报数**，而不是**集成故障**。
>
> 同理，`unknown` 一族（冷凝工况 / 水力判定等）**有意保持** `unknown`：
> `unknown` 的语义是"实体可用、值未确定"，正是那些判定想表达的
> （"冷凝工况未知" ≠ "这个实体坏了"）。

> **`frozen` 只在燃烧时判定**：冷却的管子合法地几小时不变，非燃烧时报 frozen 是误报。
>
> **未配置探头 ≠ 故障**：没装探头时 `return_temperature` / `delta_t` 显示 `unknown`，
> 但实体**仍然可用**，`probe_fault` 保持 **off**。多数安装根本没有外贴探头，
> 常亮一个故障位只会训练用户忽略它。

#### 7.5.4 怎么读 ΔT

ΔT = 供水温度 − 回水温度。**健康区间默认 5–15℃**（`DEFAULT_DELTA_T_HEALTHY_MIN` / `_MAX`）。

| ΔT | 通常意味着 | 物理原因 |
|---|---|---|
| **偏低**（< 5℃） | **流量过大**或**旁通短路** | 水走得太快，来不及把热量放给房间就回去了；旁通/水力解耦短路时尤其明显 |
| **偏高**（> 15℃） | **流量不足** | 水走得太慢，温差被拉大；可能是泵扬程不足、阀门开度不够、过滤器堵塞、或该环路阻力过大 |
| 5–15℃ | 相对健康 | 仍需结合房间实际达温效果判断 |

**关键理解：低 ΔT 和高 ΔT 都是水力信号，不是"效率好坏"。**
低 ΔT 不代表系统"效率高"，高 ΔT 也不代表"热量利用充分" ——
它们描述的是**流量与换热**，而不是燃烧效率。

> **再次强调：ΔT 不是热功率。** 真实的换热量还需要**流量**才能算
> （Q ≈ 流量 × ΔT × 比热），而本集成**不测量流量**。
> 因此**不要**用 ΔT 推算热输出、热效率或节气效果 —— 那需要流量计与燃气表，
> 本集成没有这些数据，也不宣称能算。

#### 7.5.5 `hydraulic_verdict` 每个取值的处置建议

> **⚠️ 先读懂这一句：`low_flow` / `high_flow` 是「工况标签」，不是「流量数值判断」。**
>
> 这两个键名描述的是**ΔT 落在健康区间的哪一侧**，而**不是**字面意义上的
> "流量太小 / 流量太大"。现场最容易搞反的一点是：
>
> **低 ΔT（`low_flow`）通常意味着流量其实偏大**（或旁通短路），
> **高 ΔT（`high_flow`）才意味着流量不足。**
>
> 如果你把 `high_flow` 直接读成"流量太大 → 去关小循环泵"，
> 就会把本来已经**流量不足**的系统调得更糟。
> 请始终按表格里的「物理含义 / 通常成因」两列判断，不要按键名字面理解。

| 取值 | 物理含义（ΔT 落在哪侧） | 通常成因 | 建议动作 |
|---|---|---|---|
| `low_flow` | ΔT **低于**健康下限（默认 < 5℃）—— 即"低 ΔT 工况" | **流量过大**，或**旁通短路**（热水没经过末端就回去了） | 检查**旁通阀 / 压差旁通设定**、循环泵**档位是否过高**；排查是否有回路短路、三通阀内漏。**不要**因为键名叫 low_flow 就去加大流量 |
| `high_flow` | ΔT **高于**健康上限（默认 > 15℃）—— 即"高 ΔT 工况" | **流量不足**（末端拿不到足够热量） | 检查循环泵**扬程 / 档位**、过滤器与 Y 型滤网**堵塞**、阀门**未全开**、该环路阻力过大；必要时请安装方核算。**不要**因为键名叫 high_flow 就去关小泵 |
| `ok` | ΔT 落在健康区间（默认 5–15℃）且已稳定 | — | 保持，无需处理 |
| `unbalanced` | 各需求组合之间的 ΔT 差异显著 | 各回路**水力失衡** | 做**水力平衡**：调整分集水器各支路阀芯 / 预设定；这属于安装方作业 |
| `unknown` | 数据不足，或探头不可靠 | ΔT 未稳定，或探头故障 | 先让系统连续稳定运行 **≥ 10 分钟**（默认需 `stable_seconds ≥ 600` 秒），或先按 7.5.2 修探头。数据不够时**不要**据此下结论 |

> `hydraulic_verdict` 判定需要 ΔT **稳定**一定时间（默认 600 秒）后才给结论，
> 之前一律 `unknown`。锅炉刚启停时 ΔT 本来就会剧烈变化，那不代表故障。
>
> 键名与物理成因的这层错位是**刻意的**：引擎按 ΔT 的偏离方向命名，
> 这样 `low_flow` 永远对应"低 ΔT"、`high_flow` 永远对应"高 ΔT"，
> 不会因为泵的恒压/恒流模式不同而颠三倒四。代价就是键名会被字面误读 ——
> 所以请以本表为准。

#### 7.5.6 `curve_calibration_advice` 每个取值的处置建议

> **这是纯建议。集成绝不会自动修改天气补偿曲线** ——
> 曲线由你在**配置流程**中持有，任何调整都必须由你**自己去 options 里显式执行**。
> 集成不会替你改 `supply_design` / `supply_eco` / 任何曲线点。
>
> **触发依据**：窗口内是否存在**欠温房间证据**（→ `raise_supply_curve`）
> 或**过热房间证据**（→ `lower_supply_curve`）。证据不足则为
> `none` / `insufficient_data`。

| 取值 | 含义 | 你该做什么 |
|---|---|---|
| `none` | 无欠温/过热证据，或 ΔT 健康 | 无需处理 |
| `raise_supply_curve` | 窗口内有房间**欠温**证据，且 ΔT 显示水力正常 | 可考虑**小幅上调**曲线（如把 `supply_design` 提高 1–2℃），改完观察 24 小时再看。**一次只改一个参数** |
| `lower_supply_curve` | 窗口内有房间**过热**证据 | 可考虑**小幅下调**曲线。注意降温可能让原本刚好达温的房间转为欠温，改完要回看 |
| `insufficient_data` | 样本不足（窗口内数据不够、探头不可信、或 ΔT 未稳定） | **不要**改曲线。先解决探头问题、并让系统跑满一个完整降温过程 |

**读这个建议前请先排除两件事**：

1. **房间欠温但 ΔT 偏高（`high_flow`）** —— 那不是水温不够，是**热送不过去**，
   提高水温只会让别的房间过热。请先按 7.5.5 处理水力。
2. **房间欠温但该房间根本没在要热** —— 那是阀门/执行器/日程问题，
   同样不是水温问题。对照 `sensor.<room>_setpoint_source` 与
   `binary_sensor.<room>_heat_request` 确认。

#### 7.5.7 探头失联时采暖会怎样

**不会怎样。这是硬约束，有测试支撑。**

| 场景 | 行为 |
|---|---|
| 探头读数过期/卡死/85℃ | 诊断标记为不可信；**房间目标、锅炉启停、供水温度全部不变** |
| 两路探头偏差过大 | 两路都标 `implausible`，`divergence = None`；**控制行为不变** |
| 探头实体被删除 | 同 `unavailable`；**控制行为不变** |
| **完全没装探头** | `return_temperature` / `delta_t` 显示 `unknown`，实体仍可用，`probe_fault` = off；V0.1/V0.2 的全部功能照常工作 |

探头是**纯旁观者**：它只往诊断里写数据，不参与任何仲裁或写入路径。
所以你可以在任何时候拔掉探头排查，而不用担心影响采暖。
